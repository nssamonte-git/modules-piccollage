Overview

What This Repository Is

One Gradle project that publishes reusable Android modules under the group noel.libs, all at one version.

Each creative feature is split in two. The engine module holds the logic, has no Jetpack Compose dependency, and keeps its domain code free of Android imports. The optional compose module adds ready-made UI for that engine. An app can use an engine with its own UI, or add both.

Engine modules

Editing logic, storage, rendering and export. No Compose. Example: core-creative-history-engine.

Compose modules

Optional, themeable UI that takes state and callbacks from the app. Example: core-creative-history-compose.

Origin

Where the Core Modules Come From

The feature set of the creative modules was identified from a static review of the PicCollage app, version 7.33.11. The code is an original implementation of those features.

Reference appPicCollage: Photo & Video Editor, version 7.33.11
Package reviewedPicCollage-+Photo+Video+Editor_7.33.11_APKPure.xapk
SHA-256a81bdb451fe066d48f899f8e64deec147cca28b7c183ed42439dea4a20d8a8aa
Review typeOffline static review, used to list the app's capabilities (36 topics)

What was taken

The list of features a mature collage and video editor offers, and high-level findings about how those features behave for the user.

What was written new

All code, tests, sample media and documentation in this repo. The sample uses original generated images and local, deterministic AI providers.

Not included, not claimed

No PicCollage source code, media, fonts, AI prompts, app endpoints or credentials are in this repository. The library does not claim compatibility with PicCollage documents, identical algorithms, or the same AI provider behaviour. PicCollage is a trademark of its owner; this library is not affiliated with or endorsed by it.

When a project needs features that PicCollage already offers, these modules give a tested starting point instead of a rebuild from scratch.

Proven scope

Features users already expect

The feature list comes from a shipping consumer app, so it reflects what a collage or photo and video editor needs in practice.

Transactional undo and redo, crash-safe drafts, gesture previews, GPU effects with CPU fallback, and verified MP4 export.

Your services

Typical uses: a collage or poster maker, a photo editor with erase and restore masks, a slideshow or short-video maker with music and crossfades, an editor with AI image suggestions that stay reversible, or any app that needs reliable undo, drafts and export.

Security

Mobile Build Validator: Why It Matters

A security gate that runs before the app compiles. If the source has a critical or high security problem, the build stops until it is fixed.

Security mistakes in mobile apps are cheap to fix while the code is being written and expensive after release, when the app is already on users' phones and can be pulled apart. The validator moves that check to every build, on every developer machine and in CI, so a risky change never reaches a release by accident.

What it stops

Trust-all TLS and host checks, exported components without protection, debuggable or unobfuscated release builds, committed secrets and keystores, unsafe WebView bridges, and weak or misused cryptography.

How it reports

Each finding gives the file and line, the rule, the threat it relates to, and how to fix it. A JSON report is written for CI.

No silent bypass

There is no skip switch. A finding goes away only when the code is fixed or an exception with a written reason is committed, and exceptions stay visible in every report.

Self-contained

The rules and threat cards ship inside the plugin, so it works on any machine and in CI without other repositories.

Of the 92 rules applied to Android apps, 5 are critical and 44 are high (these block); 34 medium and 9 low rules print warnings. This library runs the validator on its own code on every build.

Security

Add the Build Validator to an App

For native Android apps it is one plugin line in the root build file.

// root build.gradle.kts of the app plugins { id("noel.libs.build-validator") // from source (includeBuild) // id("noel.libs.build-validator") version "0.2.2" // from Maven Local }
  1. Build as usual. Every module's preBuild and Kotlin compile now run validateThreats first. Run it alone with ./gradlew validateThreats.
  2. Read the findings. They print above the build result. The JSON report is at build/reports/build-validator/report.json.
  3. Fix, or record a reasoned exception. Inline, on or above the line: // build-validator:ignore AND-WV-001 reason: <why>, <ticket>. Or a line RULE_ID<TAB>path-glob<TAB>reason in .build-validator-ignore at the project root.
  4. Add it to CI. Run ./gradlew validateThreats as an early CI step.
Flutter, React Native and iOS apps

Use the copy-in kit, which installs the scanner into the app and wires Gradle and Xcode:

sh "features/mobile-build-validator/validator/Flutter/install.sh" /path/to/app --with-cards # also: "React Native/install.sh", "Native IOS/install.sh", "Native Android/install.sh"
Never

Remove the plugin, lower its threshold, or suppress a finding without a real reason to get a green build.

Setup

Add the Library to a Project

Gradle pulls the modules in directly. No AAR files to copy.

1
Get the repo

Clone it next to your app.

2
Connect it

includeBuild, or publish to Maven Local.

3
Add modules

One dependency line per feature.

4
Build

The validator checks every build.

Option A: from source (best while the library is changing). In the app's settings.gradle.kts:

git clone https://github.com/nssamonte-git/modules-piccollage // settings.gradle.kts of the app pluginManagement { includeBuild("../modules-piccollage/build-validator-plugin") repositories { google(); mavenCentral(); gradlePluginPortal() } } includeBuild("../modules-piccollage")

Option B: from Maven Local (fixed versions). In the library run ./gradlew publishToMavenLocal. In the app, add mavenLocal() first in both repository lists, and give the plugin a version.

Then add the modules you need to an app module:

dependencies { implementation("noel.libs:core-creative-history-engine:0.2.2") implementation("noel.libs:core-creative-canvas-compose:0.2.2") implementation("noel.libs:core-creative-renderer:0.2.2") }

Requirements: minSdk 26 or higher, and JDK 25 to build the library. Publishing to a shared repository such as GitHub Packages is not set up yet.

Usage

Use a Module

Example: move a layer as one undoable edit, from the history engine's README.

import noel.libs.creative.history.domain.HistorySession import noel.libs.creative.model.* fun moveTitle(document: CreativeDocument) { val session = HistorySession(document) val current = session.document.value val edit = Edit.TransformLayer("page-1", "title", Transform(x = 40.0, y = 15.0)) when (val result = session.commit(EditRequest(current.revision, listOf(edit)))) { is Outcome.Success -> println("now at revision ${result.value.revision}") is Outcome.Failure -> println(result.error.code) } if (session.history.value.canUndo) session.undo() }

What your app provides

✓

One edit session per open document, created where the app wires its dependencies.

✓

Rendering, file journals and export on a worker thread, not the main thread.

✓

An app-private folder for drafts, and a FileProvider entry for sharing exports.

✓

Your own AI provider, cloud, billing and account adapters behind the library's interfaces; keys stay on your backend.

Next steps

Read the README of each module you add, then docs/creative-libraries.md for ownership and defaults. The sample/ app shows every module wired together. Check live AI providers and device-specific video codecs in your own app before release.
